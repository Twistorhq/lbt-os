## 1. What was built, per the brief

1. Document pipeline (brief item 1): stage 1 and 2 in `engine/crosschecks.py` and `engine/normalize.py`. OCR fields, MRZ (TD1, TD2, TD3 via the harness parser), and PDF417 AAMVA fields are normalized to canonical values and cross-checked field by field. MRZ check digits are verified by the harness code the benchmark scores with. Canonical source preference: MRZ for passports, barcode for United States licenses and state IDs, OCR as fallback. Disagreements between reads land as named tamper signals: front-vs-barcode where a barcode decoded, and front-vs-MRZ over the fields both reads carry (doc_number, dob, expiry) for MRZ classes; a field only one read carries is absence, not disagreement, because OCR is a best-effort read while a decoded barcode is complete by construction. (The front-vs-MRZ half landed in the fix round, M6: as first built, a passport front could disagree with its MRZ and produce no signal at all.) Date handling covers ISO, United States numeric, compact, MRZ six-digit (with the never-future rule for birth dates), and AAMVA spelled-month shapes. Document classes follow the v1 schema: government classes enabled; the school_id class shape exists end to end (consent class, document row, pipeline types) but its capture is not enabled in this phase, and the refusal is a tested behavior.
2. Face match, liveness, duplicate search (brief item 2): `engine/face.py` (cosine banding: match, review, no match; duplicate search over live templates), `engine/liveness.py` (MediaPipe landmark geometry: randomized active challenges from a four-move pool, eye-aspect and head-yaw scoring), passive MiniFASNet scoring through the harness stage. InsightFace is not imported anywhere; the embedding path is dlib via face_recognition, the same component the TW-649 FaceMatchStage scores with. Duplicate and stolen-photo search runs against stored templates at selfie time; a banned anchor anywhere in the match path refuses the attempt.
3. Decision discipline (brief item 3): on every outcome (pass, fail, review), staged images are wiped, the encrypted match payload is cleared, and both destructions are recorded as executed rows in the TW-650 `vfy_retention_actions` state machine with trigger purpose_satisfied. Only a pass persists a biometric template (AES-256-GCM ciphertext), an age attestation, and a verification state. The combiner makes a pass without an age band impossible by construction (a missing DOB routes to review), and the pass path validates its attestation inputs before the first write. Consent is re-required at decision time, before anything persists, so a mid-session withdrawal downgrades the outcome to review instead of being silently undone. Exception paths hold the same line: a failed stage wipes what it staged before the error propagates, the persist tail destroys in a finally block, and anything still staged past the 72-hour ceiling is destroyed by the staging sweep (`Staging.sweep_expired`, exposed as `pipeline.sweep_staging`). Verdicts persist as session rows; extracted fields persist only as HMAC-SHA256 hashes in `vfy_documents`. Dormancy semantics from TW-650 are untouched. (The combiner rule, the decision-time consent re-check, the exception-path wipe, and the sweep landed in the fix round: M1, M2, M5.)
4. Consent writes (brief item 4): `engine/consent.py` is the only consent writer: grant (versioned policy and retention schedule strings), require (the capture gate, evaluated before a session exists, and again at decision time before any persistence), withdraw (revoke, drop standing immediately, schedule template destruction through the retention queue with trigger verification_revocation). Rosa's TW-650 nit is closed in `supabase/migration_verify_v2.sql`: a deferred constraint trigger on `vfy_consents` revalidates the consent-type pairing when `consent_type` itself is updated, the side the v1 triggers do not watch. Behaviorally proven on live Postgres (section 4).
5. Benchmark integration (brief item 5): `engine/benchmarking.py` produces harness inputs with the engine's own components (pair scoring through the embed port and the engine cosine math; liveness presentations through the liveness port against the engine floor). `backend/app/verify/benchmark/gate.py` wires the gate run: the coverage set defaults from the registry entry; the consented-volunteer set takes its strata from a declared collection protocol record and refuses to run before the declaration exists; reports are stamped with the dataset id and the engine version. Collecting volunteers is not part of this build; only the wiring is. A synthetic end-to-end gate run (300 genuine and 5000 impostor pairs per group, two groups, deterministic embeddings) passes the gate in tests, labeled synthetic by construction.
6. Capture flag (brief item 6): `EngineConfig.production_capture_enabled` defaults to False and reads `VFY_PRODUCTION_CAPTURE_ENABLED` at deployment. `start_session` raises CaptureDisabled before anything else, including before consent and class checks; the API maps it to 403. Tests prove refusal at the pipeline level and at the HTTP level, and prove zero sessions, documents, biometrics, and staging refs exist after a refused attempt.

## 7. Design calls flagged for Rosa

1. Barcode agreement is computed only when a barcode actually decoded. An absent read cannot disagree; without this rule every passport (no PDF417 by design) would carry a permanent disagreement signal. Within a decoded barcode, the harness agreement semantics apply unchanged.
2. Velocity history persists as rows in `vfy_signals`, because the v1 schema has no attempts table. Fits the signal audit model; a dedicated table is a schema change for a later ticket if volume argues for it. Fix round (M4, the condition on Rosa's acceptance): attempt records persist under their own signal type, `velocity_attempt`, with detail {kind, key, at}; the pipeline's per-decision summary keeps the type `velocity` with its own detail shape, and `list_attempts` reads only `velocity_attempt`. As first built, both shapes shared the type `velocity` and the second decided session crashed every later velocity read.
3. The session's document class is a `vfy_sessions` column since `migration_verify_v3.sql`, written at creation and returned on the session row by both store implementations. SUPERSEDED in the fix round: as first built, the class was working state echoed into the created dict only, on the reasoning that the durable record is `vfy_documents.document_type`. Rosa rejected that as implemented (M3): `get_session` returns the raw row, which could never contain the echo, and the production pipeline died on a KeyError at the first document submission while the in-memory double, which stored the class on its session row, hid it. The column is the schema-true carrier; the in-memory double's session row now matches the real row shape, and the store tests drive the Supabase implementation through a fake client so the double is not the only witness.
4. Liveness challenge state is process-local (issued at begin_liveness, evaluated at selfie). A restart mid-session loses the challenge set and the selfie stage issues a fresh set; no durable state is affected.
5. Consent withdrawal drops standing immediately (state revoked, tier 0) while template destruction executes through the retention action queue (trigger verification_revocation, due at once). The member is in the ghost town from the moment of withdrawal; the tombstoning is the retention job's executed step, never a hard delete by the engine. Fix round (M2, Rosa accepted the design and failed its implementation): the decision path now re-requires current consent before persisting anything; a session that started before a withdrawal decides as review with the reason named (consent_not_current), persists no template, no attestation, and no tier, and the destruction block still runs.
6. The v2 guard constrains consent-type edits only where a biometric and document already pair the consent to a session. Editing an unpaired consent's type stays free (probe C). The alternative, forbidding consent_type updates outright, was rejected: a mistyped consent corrected before any capture is legitimate operations work.
7. Where a document extracts no name or number, `vfy_documents` still needs its NOT NULL hash columns, so the engine writes the HMAC of the empty string. The extraction failure itself is what the signals record; the hash column asserts nothing. Fix round (Rosa's m4 reservation on this call): the placeholder never becomes a velocity key; document velocity is recorded only when a canonical document number was actually extracted, so unreadable documents no longer share one platform-wide bucket under the empty-string hash.
8. `Pdf417Adapter` bypasses the harness stage's decode call (section 5). The harness stage fix is TW-659 (filed by Rosa, assigned to Zeke, out of scope for the TW-658 fix round): fix `Pdf417Stage` to the image API with a test against the real zxing-cpp package. The bypass stands meanwhile; field semantics stay single-sourced through `parse_aamva`.
9. The store protocol gained `get_age_attestation` so the verdict view's age band resolves identically on both store implementations.
10. The production pipeline factory (`router.get_pipeline`) reads its keys from environment variables named above. Deploy wiring (secrets provisioning, staging volume) belongs to the deploy lane (PR #9), not this build. Fix round (Rosa's m3): the factory evaluates the capture flag before reading any key material and raises the honest 403 while the flag is off, so a flag-off deployment answers 403, not a 500 KeyError, even before its keys are provisioned. Keys are mandatory only when capture is on.

## 8. Known gaps, stated plainly

- No real accuracy measurement exists yet. The engine runs end to end against deterministic fake ports and against the real zxing-cpp and passporteye packages; the OCR, detection, embedding, and liveness models have not run in this sandbox (disk and toolchain limits, section 5). The launch gate run is a later step on a benchmark machine, per section 6.
- The human-review queue's reviewer tooling is the TW-650 service layer's surface; this build lands review verdicts in the session states that surface reads. No reviewer actions are built here.
- Door Pass photo consent (Angela's second consent moment) is a TW-653 surface; this build's consent module covers the Social T2 capture classes. The Door Pass photo flow reuses `vfy_consents` with its own text version when TW-653 builds.
- Synthetic gate numbers prove wiring only. They are labeled synthetic in the registry, in the report stamping, and in these tests, and are never presented as measured accuracy.
- The duplicate search decrypts every live template on every selfie submission (Rosa's n2): correct, and fine at v1 scale, but O(N) AES-GCM decryptions on the decision path. The benchmark-machine phase must plan the corpus read deliberately (caching decrypted embeddings in-process per run is the obvious shape) instead of discovering it at scale. Noted, not fixed, by design.
- The v3 migration is covered by static contract tests and by the fake-client store tests; it was not executed against a live Postgres in the fix round (no Postgres is available in this sandbox this session). The v1 and v2 live proof (section 4) stands from the original build and Rosa's review reproduced it on her own cluster, including her added probe F.

One judgment call inside M6, stated for the verification pass: front-vs-MRZ agreement is computed over pairs where BOTH reads carry the field, not with the barcode path's one-sided-equals-disagreement rule. A decoded AAMVA barcode is complete by construction, so a one-sided field there is evidence; an OCR front read is best-effort (it routinely carries no expiry and never splits the printed name), so one-sided absence there is not. Rosa's probe case, a field both reads carry with different values, produces the named signal either way.
